# HTTP API and SSE

Status: done (roadmap item 12, merged 2026-10-10)
Depends on: [10 — Output formats](output-formats.md), [11 — Processing engine](processing-engine.md)

## Goal

Expose the queue and the transcription history over a REST API for all commands and a Server-Sent Events stream for live updates, so the frontend can upload files, control the queue and tasks, delete tasks, and read or download transcripts.

## Already decided

- [ADR 0001 — Stack and monorepo](../decisions/0001-stack-and-monorepo.md): Ktor backend serving the frontend.
- [ADR 0024 — Audio storage: original kept only until chunking, chunks stored as FLAC](../decisions/0024-audio-storage-original-until-chunking-flac-chunks.md): the upload is spooled, deduplicated by its `sha256`, and kept in the task's work directory until chunking; afterwards only the chunk FLACs exist, and playback joins them.
- [ADR 0006 — Exposed, Flyway, Kotest](../decisions/0006-exposed-flyway-kotest.md): route tests with Kotest.
- [ADR 0007 — SSE live updates](../decisions/0007-sse-live-updates.md): live updates via the Ktor SSE plugin; all commands via REST.
- [ADR 0028 — Speakers table; segments reference their speaker by `speaker_id`](../decisions/0028-speakers-table-and-segment-speaker-id.md) (item 09, done): `speakers(task_id, speaker_id, speaker)` holds one row per speaker of a task, and segments reference it by `speaker_id`. A speaker is identified by its 0-based `speakerId`; `speaker` is only ever its name ("Speaker N" as stored by the app, renamable by a later feature).
- **This item's spec is the frontend's contract** (consultation 2026-10-09): once it is `spec-approved`, items 13–15 build against it with MSW mocks, in parallel with items 09–12. The final check against the running backend is item 21.

## Proposal (approved 2026-10-09)

- **Upload.**
  - `POST /api/tasks`, multipart, with these fields:
    - `file`;
    - `language` (default `auto`, changed from `en` in the item 14 consultation, 2026-10-09), validated against [`docs/api/languages.json`](../api/languages.json) (the codes whisper-cli 1.9.2 accepts, extracted from whisper.cpp's C API, plus `auto`); anything else → `400 invalid-language`;
    - `speakers` = `auto|off|<n>`, where `1 <= n <= 20`;
    - `maxSpeakers` (default 8, `1 <= maxSpeakers <= 20`).
  - Only files whose extension is on the allow-list are accepted. The extension is checked case-insensitively, and the content type is ignored, because browsers often send generic types. The allow-list: `mp3 wav flac ogg oga opus m4a aac wma aif aiff amr webm mp4 m4v mov mkv mka 3gp`. Video files are accepted because ffmpeg extracts their audio track.
  - A file on the list that ffmpeg still cannot decode becomes a FAILED task with a readable error at CHUNKING (item 11).
  - There is no size limit. The file part is streamed (no full in-memory copy) into `TaskRepository.createFromUpload` (item 18): it is spooled with its `size_bytes`/`sha256` computed on the way, the task and its `audio` row are committed, and the original is moved to the task's work directory. No audio bytes go into the database. A failed spool (e.g. disk full) leaves no task.
  - The task is created QUEUED at the end of the queue. Returns `201` with the task.
  - A file whose bytes duplicate an existing task is rejected with `409` `duplicate-audio`, and the body names the existing task's id (see Contract).
- **Tasks.** `GET /api/tasks` (list without audio), `GET /api/tasks/{id}`.
- **Task commands.** `POST /api/tasks/{id}/pause`, `POST /api/tasks/{id}/resume`, `POST /api/tasks/{id}/cancel`, `POST /api/tasks/{id}/retry` delegate to the engine (item 11). Retry is allowed for FAILED and CANCELED tasks only: the task goes back to the end of the queue and resumes from its stored chunks. Illegal transitions per item 04, as amended by item 11 → `409`.
- **Delete.** `DELETE /api/tasks/{id}` works on any task.
  - A pending task (QUEUED, RUNNING, PAUSED) is first cancelled through the engine (its process is stopped and the cancel has finished), then deleted.
  - Deleting removes:
    - the task row, which cascades to its segments, chunks, chunk audio, and its `audio` row (so the same file can be uploaded again);
    - its work directory;
    - its cached joined FLAC.
  - `204`, or `404` for an unknown id. Emits `task-deleted`, plus `queue-updated` if the task was pending.
- **Queue.** `GET /api/queue` (paused flag + ordered task ids), `POST /api/queue/pause`, `POST /api/queue/resume`, `PUT /api/queue/order` with body `{ "taskIds": [...] }`: the full ordered list of non-terminal task ids. A different set → `409`.
- **Transcript download.** `GET /api/tasks/{id}/transcript?format=txt|srt|vtt` (json dropped 2026-10-09, [ADR 0035](../decisions/0035-no-json-download.md)), rendered on demand by item 10's renderers, served as an attachment with the matching content type. Only for COMPLETED tasks; any other status → `409 not-completed` (partial results of FAILED/CANCELED tasks are kept only for a retry).
- **Turns for the transcript view.** `GET /api/tasks/{id}/turns` returns the task's speakers (id and stored name) and item 09's speaker turns, each with its segments, so turn merging exists only in Kotlin. Turns reference their speaker by `speakerId`, so a later rename changes one name and no turn. The JSON download stays the oracle format.
- **Audio.**
  - `GET /api/tasks/{id}/audio` joins the task's stored chunk FLACs in `idx` order with ffmpeg's concat demuxer (`-c copy`, no re-encode) into one FLAC, served as `audio/flac` (16 kHz mono, ADR 0024).
  - The joined file is built once into `$STT_DATA_DIR/tmp/<task-id>.flac`: written under a temporary name and renamed, one build per task at a time.
  - It is served with HTTP Range support, so the browser can seek and item 15 can offer click-to-seek.
  - The cache is removed when the task is deleted, and at startup (`tmp/` is emptied when the database opens).
  - A task without stored chunks (not chunked yet, or canceled or failed before chunking) → `404`. The Task's `hasAudio` field tells the client in advance.
- **Events.** `GET /api/events`, an SSE stream of the engine's `SharedFlow<Event>` (item 11).
  - On every connect the first event is `snapshot` (all tasks + queue); live events follow.
  - `task-updated` carries the full task, so applying any event twice is harmless and the client needs no refetch after reconnecting.
- **Errors.** Body `{ "error": "<code>", "message": "..." }`, with `taskId` added for `duplicate-audio` only. No stack traces in responses.
- JSON via kotlinx.serialization; route handlers stay thin and call the engine/repositories.

## Contract (approved 2026-10-09)

The JSON shapes the frontend builds against.

- **Example files.** One example JSON file per response body, SSE event payload and error lives in [`docs/api/`](../api/) (created 2026-10-09). The file-to-shape mapping and the nullability convention are in [`docs/api/README.md`](../api/README.md).
  - Item 13's MSW handlers serve these files.
  - This item's route tests check that every real response has the example's structure: the same keys, value types and nullability.
  - A contract change edits the example file and this section in the same commit.
- **Task.**
  - Fields:
    - `id` (number)
    - `filename` (string)
    - `status` (`QUEUED|RUNNING|PAUSED|COMPLETED|FAILED|CANCELED`)
    - `phase` (`CHUNKING|TRANSCRIBING|DIARIZING|null`)
    - `language` (string)
    - `speakersMode` (`auto|off|fixed`)
    - `speakersCount` (number, or null unless `fixed`)
    - `maxSpeakers` (number)
    - `durationMs` (number, or null before chunking)
    - `sizeBytes` (number)
    - `hasAudio` (boolean): whether the task has stored chunk FLACs, i.e. whether `GET /api/tasks/{id}/audio` serves audio (added 2026-10-09, item 15 consultation)
    - `transcriptionProgress` (0–1)
    - `diarizationStage` (`EMBEDDING|CLUSTERING|null`)
    - `diarizationProgress` (0–1, or null)
    - `error` (string or null)
    - `transcribedUntilMs` (number, or null): the end of the task's last stored segment, on the `/audio` timeline; null while no segment is stored
    - `createdAt`, `startedAt`, `finishedAt` (epoch ms, or null)
  - `diarizationStage` is the running diarization stage: `EMBEDDING` (segments embedded) and then `CLUSTERING` (merges done). It is null outside the DIARIZING phase (added 2026-10-09, item 11 consultation).
  - `diarizationProgress` is the progress within the current stage, so the diarization bar fills once per stage, labelled by stage. Before diarization starts it is 0; once the speakers are stored it is 1. It is `null` when diarization does not apply: speakers `off`, or the task finished without segments.
  - `phase`:
    - the phase the task is in while RUNNING or PAUSED;
    - FAILED and CANCELED tasks keep the phase they stopped in, so the UI can say e.g. "failed while transcribing at 12:34" (with `transcribedUntilMs`);
    - null for QUEUED tasks (also after a retry or a restart) and COMPLETED tasks.
  - `transcribedUntilMs` is computed from the stored segments (no new column). Segments are committed per chunk (ADR 0004), so a retry resumes at the first chunk not DONE, which starts at or after this time. At most one chunk is redone.
  - `hasAudio` is computed from the stored chunk audio (no new column). It is false until chunking has stored the chunk FLACs, and stays false for a task cancelled or failed before that; it becomes true in the same transaction that stores the chunks (item 18), so `task-updated` reports it.
- **Task list** (`GET /api/tasks`): `{ "tasks": [Task] }`. Pending tasks come first, in queue order, then finished tasks, newest `finishedAt` first.
- **Queue:** `{ "paused": boolean, "taskIds": [number] }` (pending tasks in queue order).
- **Responses by route:**
  - upload → `201` Task;
  - pause/resume/cancel/retry → `200` Task;
  - queue pause/resume/order → `200` Queue;
  - delete → `204` without a body;
  - rename a speaker, merge speakers, reset all merges → `200` Speakers (item 22).
- **Turns** (`GET /api/tasks/{id}/turns`): `{ "speakers": [{ "speakerId", "speaker" }], "turns": [{ "speakerId" | null, "startMs", "endMs", "text", "segments": [{ "startMs", "endMs", "text" }] }] }`.
  - `speakers` are the task's **effective** speakers (item 22): its rows of the `speakers` table (ADR 0028) except those merged into another speaker, ordered by `speakerId`: `speakerId` the 0-based number, `speaker` the stored name (`"Speaker N"`, N = `speakerId` + 1, until renamed). A rename changes only the name here, never the turns, which reference their speaker by `speakerId`. A merged speaker's segments carry the `speakerId` of the speaker it was merged into, so its turns join that speaker's neighbouring turns.
  - `turns` are item 09's `speaker_turns`: consecutive segments with the same `speakerId` form one turn. A turn names its speaker only by `speakerId`; the UI shows the name from `speakers`.
  - Only for COMPLETED tasks; any other status → `409 not-completed`.
  - Times: `startMs`/`endMs` of turns and segments are milliseconds on the timeline of `GET /api/tasks/{id}/audio`. The joined audio starts at 0, and item 06's chunks are contiguous and cover `[0, durationMs)`, so a segment's stored time is its position in the played file. Segments and turns come in transcript order. There can be gaps between segments (silence), where no segment is playing. So the transcript view can highlight the segment being played (item 15): the one whose `[startMs, endMs)` contains the player's current time.
  - With speakers `off`: `speakers` is empty, and there is one turn per segment with `speakerId: null`.
  - Text ([ADR 0030](../decisions/0030-trimmed-segment-text-in-all-outputs.md)): every segment `text` is trimmed; a turn's `text` is its segments' non-blank trimmed texts joined with single spaces (a blank segment must not leave a double space, user decision 2026-10-10).
- **Speakers** (added 2026-10-10, item 22): `{ "speakers": [{ "speakerId", "speaker" }] }`, the task's speakers ordered by `speakerId` ([`docs/api/speakers.json`](../api/speakers.json)).
  - `PUT /api/tasks/{id}/speakers/{speakerId}` with `{ "speaker": "<name>" }` renames one speaker. The name is stored as sent; clients trim it first (user decision 2026-10-10). Leading or trailing whitespace, empty, longer than 40 characters, or a control character anywhere → `400 invalid-speaker-name`, nothing changes. A name another speaker of the task already has, compared case-insensitively and including speakers hidden by a merge → `409 duplicate-speaker-name`; a speaker's own current name is no duplicate (user decisions 2026-10-10). `{ "speaker": null }` resets the name to `"Speaker N"` (N = `speakerId` + 1), written by the server and checked for duplicates like any other name.
  - `POST /api/tasks/{id}/speakers/merge` with `{ "group": [<speakerId>, …], "into": <speakerId> }` folds every other member of `group` into `into`, which keeps its id and name; the answer is the task's effective speakers. No segment row is rewritten: the merge is a mapping resolved when the transcript is read, so it can be undone. The downloads (txt, srt, vtt) label a merged speaker's segments with the survivor's name, in the survivor's turns. `into` not in `group`, a group naming fewer than two speakers, or a member (or `into`) already merged into another speaker → `400 invalid-merge`, nothing changes.
  - `DELETE /api/tasks/{id}/speakers/merges` ("Reset all merges") removes every merge of the task; the answer is all its speakers again, each with the name its row kept, and the turns and downloads are as before the first merge.
- **Events** (`event:` name → `data:` JSON):
  - `snapshot` → `{ "tasks": [Task], "queue": Queue }`
  - `task-updated` → Task
  - `task-progress` → `{ "id", "transcriptionProgress", "diarizationStage", "diarizationProgress" }`
  - `queue-updated` → Queue
  - `task-deleted` → `{ "id" }`
  - `speakers-renamed` → `{ "id", "speakers": [{ "speakerId", "speaker" }] }` (item 22): after a stored rename or name reset, the task's speakers as stored; a rejected rename emits nothing
  - `speakers-merged` → `{ "id", "speakers": [{ "speakerId", "speaker" }] }` (item 22): after a stored merge or a reset of all merges, the task's effective speakers; a rejected merge emits nothing. Turns can join or split along a former boundary, so a client showing the task's transcript refetches `/turns`
- **Error codes:**

  | Status | Codes |
  | ------ | ----- |
  | `400` | `missing-file`, `unsupported-format`, `invalid-language`, `invalid-speakers`, `invalid-max-speakers`, `invalid-transcript-format`, `invalid-speaker-name`, `invalid-merge` (item 22) |
  | `404` | `not-found` (unknown task), `no-audio` (task without stored chunks) |
  | `409` | `illegal-transition`, `reorder-mismatch`, `duplicate-audio` (with `taskId`), `not-completed` (turns or transcript of a task that is not COMPLETED), `duplicate-speaker-name` (item 22) |
  | `500` | `internal` |
- **Mock additions from item 13** (added 2026-10-09): the frontend workspace added [`docs/api/task.paused.json`](../api/task.paused.json) and [`docs/api/task.canceled.json`](../api/task.canceled.json), because no example had those statuses, and it recorded where its mocks must deviate from this contract. That list is the "Mock additions to settle with item 12" section of [the frontend foundation spec](frontend-foundation.md); this item's route tests adopt the two examples and settle each deviation (item 21 verifies the rest end to end).
- **Task transition table** (added 2026-10-09, item 13 consultation): [`docs/api/task-transitions.json`](../api/task-transitions.json) lists the allowed status transitions and, for each command endpoint, the statuses it accepts. The frontend reads it to offer only allowed commands; the backend checks that its `TaskStatus` table equals it (item 11). A command outside the table still answers `409 illegal-transition`.
- **Languages** (added 2026-10-09, item 14 consultation): [`docs/api/languages.json`](../api/languages.json) lists the language codes and names the upload accepts (whisper-cli 1.9.2's table plus `auto`) and the default, `auto`. The upload form's select reads it, and this item validates `language` against it.

## Open questions (answered 2026-10-09)

- Upload size limit? → **None**: uploads are streamed to disk; a failed spool leaves no task.
- Accepted formats? → **Extension allow-list, audio and video** (list above). The content type is ignored.
- Range support for `/audio`, caching? → **Range, with the joined FLAC cached in `$STT_DATA_DIR/tmp`** until the task is deleted or the app restarts.
- Delete endpoint? → **Yes, for any task**: a pending task is cancelled through the engine first. Deleting frees the `sha256`, so a file whose task FAILED or was CANCELED can be uploaded again.
- Initial state on `/api/events`? → **The server sends a `snapshot` first**; `task-updated` carries the full task.
- Add item 10 to `Depends on`? → **Yes.**
- Upper bound for `maxSpeakers` and a fixed `<n>`? → **20** for both (items 14's inputs use the same bound).
- Duplicate upload response? → **`409` `duplicate-audio` with `taskId`.**
- Where does the transcript view get turns? → **`GET /api/tasks/{id}/turns`.**
- Where do the contract examples live? → **`docs/api/`.**
- `language`? → **Validated against whisper-cli's language codes plus `auto`**; otherwise `400 invalid-language`.
- `/turns` for a task that is not COMPLETED? → **`409 not-completed`.**
- `/turns` with speakers `off`? → **One turn per segment, `speaker: null`.**
- `phase` of FAILED and CANCELED tasks? → **Kept**: the phase the task stopped in. Plus a new field, `transcribedUntilMs` (end of the last stored segment), for "failed while transcribing at <time>". Resume stays per chunk (ADR 0004): segment-level resume was considered and rejected (it would commit segments while whisper-cli streams them and restart inside a chunk, possibly in the middle of speech).
- Is segment text trimmed? → **Yes, everywhere it leaves the backend**, the API and every download format ([ADR 0030](../decisions/0030-trimmed-segment-text-in-all-outputs.md); its json point was dropped with the json download, [ADR 0035](../decisions/0035-no-json-download.md)). Storage stays untrimmed for item 07's prompt.
- Which download formats? → **txt, srt and vtt** (ADR 0035); speaker labels in them are the stored speaker names ([ADR 0034](../decisions/0034-speaker-labels-are-stored-names.md)).

## Test list (written with the user; Canon TDD step 1)

Approved 2026-10-09 with the spec. Behaviors only; discovered scenarios are appended as `(discovered)` and confirmed with the user.

- [x] Uploading a file creates a QUEUED task at the end of the queue, records its `size_bytes`/`sha256`, and keeps the original in the task's work directory (no audio bytes in the database)
- [x] Uploading without a file, with an extension outside the allow-list, with a language not in `docs/api/languages.json`, or with an invalid `speakers` or `maxSpeakers` value (outside 1–20), is rejected with 400 and the matching error code; an upload without `language` gets `auto`
- [x] Uploading the same bytes again is rejected with 409 `duplicate-audio` naming the existing task's id
- [x] (discovered, confirmed 2026-10-10) A non-numeric `maxSpeakers` (e.g. `many`) is rejected with 400 `invalid-max-speakers`, not silently defaulted
- [x] (added 2026-10-10, review finding, observation point confirmed with the user) Uploads are streamed to the spool, no full in-memory copy: uploading a file larger than the configured buffer does not read it fully into memory, and the duplicate check still answers 409 with the existing task's id when the spooled bytes match. Observation point (user-chosen option 1): the new spool path driven with a `SpoolWatchingSource` keeps the largest unspooled window ≤ 1 MiB and the stored sha256 equals the true digest; a duplicate yields the existing id with no task row, work directory or audio row; plus an HTTP upload of ≈2.5× the window through the real multipart route answers 201 with the right size and, for the same bytes, 409 naming the first task.
- [x] Listing tasks returns pending tasks in queue order, then finished tasks newest first, without audio data
- [x] Requesting an unknown task returns 404 with an error body
- [x] Pausing, resuming, cancelling and retrying a task reach the engine and return the updated task
- [x] An illegal task command (e.g. pausing a COMPLETED task, retrying a COMPLETED or QUEUED task) returns 409
- [x] Deleting a finished task removes it with its segments, chunk audio, work directory and cached audio; the same file can then be uploaded again
- [x] Deleting a pending task cancels it through the engine first, then removes it
- [x] Reordering with the full set of non-terminal ids changes the queue order
- [x] Reordering with a different set of ids returns 409 and leaves the order unchanged
- [x] Pausing and resuming the queue is reflected in `GET /api/queue`
- [x] Downloading a transcript as txt, srt and vtt returns the rendered output with the right content type (json dropped 2026-10-09, ADR 0035)
- [x] Downloading with an unknown format returns 400; downloading the transcript of a task that is not COMPLETED returns 409 `not-completed`
- [x] The turns endpoint returns the task's speakers with their stored names and item 09's turns (by `speakerId`) with their segments for a COMPLETED task; with speakers `off`, no speakers and one turn per segment with `speakerId` null; 409 `not-completed` for any other status
- [x] (added 2026-10-09, from the phase/trim decisions) Turn and segment texts in `/turns` are trimmed, and a turn's text is its segments' trimmed texts joined with single spaces
- [x] (added 2026-10-09, from the phase/trim decisions) A FAILED or CANCELED task keeps the phase it stopped in, and `transcribedUntilMs` is the end of its last stored segment (null without segments); QUEUED and COMPLETED tasks have no phase
- [x] Audio download returns one FLAC (`audio/flac`) joining the task's stored chunks in order; a task without stored chunks returns 404, and its `hasAudio` is false (true once chunks are stored) (hasAudio added 2026-10-09)
- [x] A Range request for the audio returns 206 with the requested bytes of the joined FLAC
- [x] An SSE client first receives a `snapshot`, then `task-updated`, `task-progress`, `queue-updated` and `task-deleted` events as the engine emits them
- [x] (added 2026-10-10, user decision at the first checkpoint) An SSE client that falls behind the engine's event buffer is disconnected instead of silently missing events, and on reconnecting it receives a fresh `snapshot`
- [x] Every response and event payload has the structure of its `docs/api/` example
- [x] (discovered, confirmed 2026-10-10) Requesting a known task returns 200 with the task
- [x] (discovered, confirmed 2026-10-10) Requesting a task by a non-numeric id (e.g. `/api/tasks/abc`) returns 404 `not-found`

## Acceptance criteria

- Every route has a Ktor `testApplication` test, including its 404/409 paths.
- An SSE test receives the snapshot and then the events in emission order.
- Uploading a large file does not load it fully into memory (verified by streaming design and a test with a file larger than the configured buffer).
- Error responses always use the `{ "error", "message" }` body.
- Every response and event shape matches its `docs/api/` example.
- All test-list items ticked and green; user approved the diff.
