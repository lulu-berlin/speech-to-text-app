# 42 — Worker stability: no per-task exception may leave the task stuck or kill the queue, and no command may race a task's start

Status: done (roadmap item 42, approved 2026-10-18)
Depends on: [11](processing-engine.md) (done)
Blocks: —

## Goal

Whatever a single task's run throws — during setup, a phase, or a repository call — the task ends in a defined state and the worker keeps taking the next queued task. And a cancel, pause or delete that arrives while the worker is starting a task acts on that task's run exactly as it would a moment later: the process is stopped or frozen, and the status the command stored is the one the task keeps.

## Already decided

- Reported 2026-10-12 by a third-party source review of `main`, triaged by the root agent against the code (the finding holds).
- Evidence (`ProcessingEngine.runTask()`): `setRunningIfQueued` is followed by the settings lookup (`settings.get()`, item 32) and the work-directory creation **outside** the `try` that catches processing failures. A throw in either leaves the task `RUNNING` (no `failIfRunning`) with no worker inside it, until a restart's recovery re-queues it. The exception ends only the task's own job: that job runs in the engine's scope, a `SupervisorJob` (`EngineModule.kt:39`), and `runInJob`'s `job.join()` does not rethrow the job's failure, so the worker coroutine survives and moves on (corrected 2026-10-16, cycle 2's red: the next task completed). The worker coroutine itself does end on a throw from its own reads in `nextTask()` (`ProcessingEngine.kt:413-423`), which run outside any task's job, and `workerLoop()` (`:425-434`) has no catch: the queue then stops until a restart (added 2026-10-16 from code reading).
- Cancellation must stay distinct from ordinary failure (the existing `catch (e: CancellationException) { throw e }` is the contract to preserve).
- [ADR 0046](../decisions/0046-every-feature-has-an-e2e-test.md): the fix carries an e2e assertion that the queue survives an unexpected task failure.
- Added 2026-10-16 (the user, from `docs/known-issues.md`'s HIGH backend row, found in the 2026-10-13 review): **commands race a task's start.** `runInJob` launches the task's job (`ProcessingEngine.kt:449`, `scope.launch { runTask(task) }`) and registers it in `running` only afterwards (`:454`), so the job is already running when a command looks it up through `runningJob(id)` (`:480`). A command in that window gets `null`:
  - `cancelTask` (`:349-350`) skips `cancelAndJoin()` — the process is not stopped — yet `cancelIfPossible` stores CANCELED, since it accepts a RUNNING task (`db/TaskRepository.kt:321`);
  - `pauseTask` (`:216-220`) stores PAUSED with `runningHere` false, so neither the process nor the pause gate is frozen;
  - `deleteTask` goes through `cancelTask` (`:264-267`), so the row is deleted while the run continues.
  The run then finishes and `setCompleted` (`:508`; `db/TaskRepository.kt:273-282`, no status condition) overwrites the stored CANCELED or PAUSED with COMPLETED. The window is short (from `launch` to the registration), but the outcome is a wrong stored state.
- Item 40 keeps `setCompleted` the durable terminal write (`docs/specs/atomic-task-transitions.md:29`): a pause landing while the last process exits loses to the completion. That rule stays; this amendment closes the window instead of making the completion conditional.

## Decided (consultation, 2026-10-13)

- **Guarded path**: every task-specific step — `setRunningIfQueued`, the settings lookup (item 32), setup, `runInJob`'s phases and finalization — is inside the guarded path; any non-cancellation throw there marks the task FAILED with the message (today's rule) and the worker continues.
- **Loop guard** (amended 2026-10-17, the user; replaces the 2026-10-13/16 wording, which promised a terminal state even when the failure could not be recorded — only a retry of the failed write could keep that): if the write that records a task's failure throws, the engine logs it at error level with the task's id, the original failure and the write's error, and writes nothing more. The task stays RUNNING until a restart's recovery queues it again; nothing retries the write. The task's job ends and the worker takes the next queued task.
- **Cancellation stays distinct** (refined 2026-10-17): a cancellation of the task's own coroutine (the app quitting, a user cancel or delete) is rethrown (item 11/34 contract; "11/36" before, a typo — item 36 is follow mode); only shutdown ends the loop. It is never a FAILED.
- **A killed process is an interruption** (2026-10-17, the user): a task is RUNNING only while a process works on it. If its process is killed by SIGTERM while the app keeps running (`ProcessRunner` surfaces it as a `CancellationException` while the task's coroutine is still active), the task goes back to QUEUED at once (phase cleared, queue position kept), and the engine runs it again from its interrupted chunk. If the app quits, the next start does the same (restart recovery); nothing is written at quit time, since a crash cannot write either and the startup recovery covers both. RUNNING → QUEUED becomes an allowed transition (ADR 0057; no INTERRUPTED status: it would last one write and cost a migration, API types and UI labels). Known tradeoff: something that keeps killing the process makes the task rerun each time.
- **Start race in scope** (2026-10-16, the user): the start race is planned here, not as its own item — it touches the same `runInJob`/`runTask` path.
- **No e2e for the start race** (2026-10-16, the user; ADR 0046): the window lasts from `launch` to the registration, which a browser cannot reach on purpose, so a browser test would pass with or without the fix. Deterministic engine tests are the proof; the item's existing e2e (a task that fails mid-run does not stop the queue) covers its user-visible feature.

- [x] A process killed by SIGTERM while the app keeps running is never a failure: the task goes back to QUEUED, and the engine runs it again from its interrupted chunk

- [x] (must not break) The engine suites (`ProcessingEngineFailureSpec`, …) stay green
- [x] (amendment) A cancel that arrives while the worker is starting the task stops that run's process and the task stays CANCELED — never overwritten with COMPLETED
- [x] (amendment) A pause that arrives while the worker is starting the task freezes that run (process and pause gate) and the task stays PAUSED until it is resumed; resuming continues it to COMPLETED
- [x] (amendment) A delete that arrives while the worker is starting the task stops that run's process before the row is gone, and the run writes nothing afterwards

- [x] (discovered, added to scope by the user) A throw from the worker's own reads while it looks for the next task (`nextTask()`: queue state, the started paused task, the next queued task) does not end the worker: it logs the failure with its reason and keeps taking queued tasks once the reads succeed again
- [x] (discovered) Quitting the app while a task is RUNNING kills its process; the next start marks the task QUEUED, and the engine runs it again from its interrupted chunk
- [x] (discovered) A process killed by SIGTERM during diarization sends the task back to QUEUED, and the engine runs it again
