# 0024 — Audio storage: original upload kept only until chunking, chunks stored as FLAC

Status: accepted · Date: 2026-10-07 · Supersedes: [0005](0005-audio-as-sqlite-blob.md), [0018](0018-audio-payload-paged-blobs.md)

## Context
ADR 0005 stored the uploaded audio as a SQLite BLOB; ADR 0018 paged it into 1 MiB `audio_parts` rows and kept it after completion for history playback, so the database held every original upload in full. Processing only ever uses the audio as 16 kHz mono: whisper-cli transcribes ~5-minute chunks (ADR 0004), and the speaker model reads 16 kHz PCM (ADR 0003). Playback of speech does not need the original quality.

Evidence for FLAC chunks (gathered by the user in the item 06 workspace with the devenv tools, 2026-10-06):
- Lossless: a 60 s 16 kHz mono s16 clip (tone + pink noise) decoded WAV → FLAC → raw s16 is byte-identical (`cmp`). Size: WAV 1 920 078 B, FLAC 1 097 037 B (57 %); about 65 MB per hour of FLAC (estimate; speech not measured), against about 115 MB/h for 16-bit WAV and about 58 MB/h for 128 kbit/s MP3.
- whisper-cli 1.9.2 reads FLAC: `whisper-cli --help` lists `supported audio formats: flac, mp3, ogg, wav`. The same 8 s clip as WAV and as FLAC gives `processing … (128000 samples, 8.0 sec)` both times and identical `-oj` JSON (model `ggml-large-v3-turbo-q5_0`, `--no-gpu`). whisper.cpp v1.9.2 `examples/common-whisper.cpp` decodes every input via miniaudio to f32 mono 16 kHz; the README line "currently runs only with 16-bit WAV files" is out of date relative to that code.

Duplicate detection (ADR 0018: `audio.sha256` UNIQUE) was considered on other inputs and rejected:
- SHA-256 of the decoded PCM matches only lossless or metadata-only differences (tags, WAV↔FLAC). It misses lossy re-encodes (MP3 vs WAV, other bitrates; encoder padding shifts samples), can change across ffmpeg versions, and is only known after decoding, so a duplicate would surface in the CHUNKING phase instead of at upload.
- An acoustic fingerprint (Chromaprint `fpcalc`) matches approximately, adds a dependency, has false positives, and is built for music.

## Decision
1. **Duplicate detection stays on the original upload bytes.** `audio(task_id PK, size_bytes, sha256 UNIQUE)` is unchanged: `size_bytes` and `sha256` are computed on the upload stream while it is spooled, before anything is decoded, and a duplicate is rejected at upload. The strict rule of ADR 0018 stays (a FAILED or CANCELED task also blocks the same bytes) and outlives the original: the `audio` row is kept after the original is deleted.
2. **The original upload is not stored in the database.** The upload is spooled into `$STT_DATA_DIR/tmp` (ADR 0017) with size and sha256 computed on the way; one short write transaction inserts the task row and its `audio` row. After the commit, the spool file is renamed (same filesystem, atomic) to `$STT_DATA_DIR/work/<task-id>/source`, so no spool remains in `tmp/` after the commit; a rejected duplicate or any failed transaction deletes the spool. The original stays in the work directory until its task is chunked and is deleted only after the chunk plan and all chunk FLACs are committed to the database. If a crash leaves the original behind after that commit, the engine deletes it when it next finds the task's stored plan. A task that becomes terminal before chunking loses its original with its work directory, and deleting a task (item 12, if a delete endpoint is added) deletes its work directory at once. If the original is missing when CHUNKING starts (for example a crash between the commit and the rename: the spool was removed from `tmp/` at the next open), the task fails with an error naming the missing original.
3. **Chunks are stored as FLAC, 16-bit, 16 kHz mono**, replacing the 16-bit WAV (`pcm_s16le`) chunk export decided earlier in item 06. Storage: a side table `chunk_audio(task_id, idx, flac BLOB NOT NULL, PRIMARY KEY (task_id, idx), FOREIGN KEY (task_id, idx) REFERENCES chunks (task_id, idx) ON DELETE CASCADE)`, one BLOB per chunk. One chunk is held in memory at a time on write and read; that is bounded because item 06 caps a chunk at 6 min: at most 6 × 60 × 16 000 × 2 B = 11.52 MB even when FLAC cannot compress (about 6–7 MB expected). Paging (ADR 0018) is not used: it existed for unbounded uploads. Queries on the plan (`chunks`) never read `chunk_audio`. The chunk plan and all chunk FLACs of a task are written in one transaction.
4. **Schema change through a migration.** `V2` drops `audio_parts` and creates `chunk_audio` (ADR 0019: later items extend the schema only through migrations). Roadmap item 18 owns the migration and the repository changes; item 11 (engine) depends on it.
5. **Audio after chunking comes only from the stored chunks:**
   - Transcription (items 07/11): each chunk FLAC is written from the database to a file in the task's work directory for whisper-cli.
   - Diarization (items 08/09/11): the whole-file PCM is always rebuilt from the stored chunks — each FLAC decoded in `idx` order and concatenated — with or without a restart, so speaker labels do not depend on restarts. The PCM is therefore 16-bit-quantized, unlike the oracle's float32 decode of the original.
   - Playback (items 12/15): `GET /api/tasks/{id}/audio` joins the task's chunks with ffmpeg's concat demuxer (`-c copy`, no re-encode) into one FLAC, served as `audio/flac`. Caching and HTTP Range support are decided in item 12.

## Consequences
- Supersedes ADR 0005 and ADR 0018. Carried over from them: the `audio` metadata row, the strict `sha256` duplicate rule, spooling the upload before taking the write lock (ADR 0018); listings never read audio, temporary files are per task (ADR 0005).
- The database is no longer the only copy of audio: for tasks not yet chunked, the original lives only in `$STT_DATA_DIR/work/<task-id>/source`. Backups must take the whole `$STT_DATA_DIR` (`stt.db` and `work/`), not just the database file.
- Item 11's startup cleanup keeps the work directories of pending tasks (QUEUED, RUNNING, PAUSED) because unchunked ones hold their original; it removes those of terminal or deleted tasks.
- Disk: an upload occupies its size in `tmp/`, then in `work/` (renamed, not copied) until it is chunked. The database grows by the chunk FLACs (about 65 MB per hour of audio, estimated) instead of the upload size. The chunking transaction writes all chunk FLACs at once, so the WAL grows by that amount until the next checkpoint (ADR 0017's `journal_size_limit` still applies).
- Playback is 16 kHz mono; the original format, quality and metadata are not retrievable. `tasks.original_filename` and `tasks.content_type` describe the upload for display only. A task that is canceled or fails before chunking keeps no audio at all (only its `audio` metadata row); its audio endpoint answers 404.
- Re-chunking a finished task with other parameters is impossible; re-transcribing it with another model still works from the stored chunks.
- `V2` drops existing `audio_parts` rows. Databases created before `V2` (development only; nothing has been released) lose their stored originals, and their pending tasks fail at CHUNKING with the missing-original error.
- Item 06 exports the chunks as FLAC instead of WAV (amended in its own workspace).
