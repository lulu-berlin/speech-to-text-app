# 0020 — Process runner: JNA signals, process groups, cancellation

Status: accepted · Date: 2026-10-06

## Context
The backend must run external tools (ffmpeg, whisper-cli). ADR 0004 requires pausing the current whisper-cli process with `SIGSTOP` and resuming with `SIGCONT`. Java exposes no signal API: `Process.destroy()`/`destroyForcibly()` send `SIGTERM`/`SIGKILL` to the direct child only, and there is no way to set a process group before exec (`posix_spawn` does it, but JDK does not expose the flag). ADR 0001 requires all async work on coroutines. Command failure must surface exit code and stderr; long runs stream output line by line.

## Decision
- `stt/process/ProcessRunner` (Kotlin): `suspend fun run(cmd, onStdoutLine = {}, onStderrLine = {}): ProcessResult(exitCode, stdout, stderr)`. Callbacks stream each line as it is written; the result captures both streams (stdout for order/amount, stderr for error messages).
- Every command is spawned as `setsid <cmd…>` (util-linux): the run owns a fresh session and process group, and the direct child's pid is the group id (in the normal case setsid execs the command without forking). All signals target the group (negative pid), so the whole process tree — not just the direct child — is stopped, resumed, and killed.
- Signals are sent with JNA `kill(2)` (`com.sun.jna.Native.load("c", …)`): `pause()` = `SIGSTOP` to the group, `resume()` = `SIGCONT`. No `kill` binary is spawned. Signal numbers are the Linux constants (SIGSTOP 19, SIGCONT 18, SIGTERM 15, SIGKILL 9); the app targets the Linux Nix build.
- Any failure of `run` kills the tree: cancellation of the caller, a throwing callback (also after the direct child has exited), or any other exception. The failure path sends `SIGCONT` first (harmless if not stopped; lets a signal handler run its cleanup), then `SIGTERM`, waits the grace period, then `SIGKILL`, then waits at most the grace period again; if the group still has members (unreaped zombies, e.g. the JVM as PID 1 without an init; processes in uninterruptible sleep), it logs a WARN naming the group and continues. `run` then rethrows the original exception. Worst-case cancel latency is 2 × grace.
- Grace period between `SIGTERM` and `SIGKILL` (and the bound on the wait after `SIGKILL`) defaults to 2 s; it is a constructor parameter (integration tests inject a short grace).
- Spawning is not cancellable: a process, once started, is always registered as the run's group before cancellation is observed, and the cancel is then observed inside the block whose failure path terminates the group. A cancel that lands while `start()` runs therefore never leaks an unregistered, unkillable process.
- The group may not exist yet when the run registers it: `start()` returns as soon as `setsid` is started, but `setsid` calls `setsid()` only after its dynamic libraries load (measured: the group was missing right after `start()` in about 1 of 8 spawns), and `kill(-pid, …)` then fails with `ESRCH`. Every signal of the run therefore goes to the direct child's pid first, then to the group, and the live direct child counts as a member when waiting for the tree to die. Until `setsid()` runs, the child is the whole run: a pause stops it before it can create the group, and a cancel terminates it before it can create the group or fork into it; signalling the child before the group means a stopped or dead child cannot add processes the group signal would miss. The child's pid is signalled only while the `Process` reports it alive (unreaped), so a reused pid is not hit beyond the pid-reuse race already accepted below. Rejected: waiting in the spawn until `getpgid(pid) == pid` — any polling interval leaves the command running unpaused between the group's creation and the next poll (one line escaped with a 50 ms poll), and it needs an extra bound and error.
- Cancellation is observed via 50 ms `waitFor` polling with `ensureActive()` (blocking waits themselves are not interruptible). Buffered but undelivered lines are dropped: the drain coroutines are children of `run` and check cancellation before every line, so no line reaches a callback after the cancel.
- stdout and stderr are drained concurrently by two child coroutines on `Dispatchers.IO` so a full pipe buffer never blocks the child; callbacks must be non-blocking. Once the direct child is dead, each drain reads what is still available before it stops, so output written immediately before exit is never lost.
- stdin is redirected from `/dev/null`: a tool that reads stdin to EOF (ffmpeg without `-nostdin`) finishes instead of hanging.
- `pause()`/`resume()` are no-ops while no run is in flight (the run's group registration is cleared when `run` returns). During a run they target the group even after the direct child has exited, so surviving descendants are still stopped and continued; `kill(2)` errors are ignored (the pid-reuse race is accepted).
- The pause state is a per-run flag, alive from `run` entry to `run` exit: a `pause()` issued before or during spawn takes effect right after spawn (`SIGSTOP` to the child and the group once the group is registered, so it holds even before `setsid()` has created the group); `resume()` clears it; it is cleared when `run` ends, so a leftover pause (e.g. a task cancelled while paused) never freezes the next run. Task-level pause across chunks is the engine's concern (item 11).
- Non-existent executables fail fast: the executable is resolved against PATH before spawning, and a miss throws `ExecutableNotFoundException` whose message names the command. Other `start()` failures (e.g. a missing `setsid`, a permission error) propagate as the `IOException` naming the program; wrapping them would misreport the user's command as missing.
- Blocking I/O and waits only inside `withContext(Dispatchers.IO)`; no raw `Thread`, `ExecutorService`, or `CompletableFuture`.
- Output is line-oriented. Binary stdout (e.g. ffmpeg raw PCM) is out of scope; the audio item reads files or adds a byte mode.
- The runner is single-flight (one active process, matching the queue that processes one task at a time) and enforces it: a second `run` while one is in flight fails fast with `IllegalStateException` and leaves the first run untouched; `pause()`/`resume()` address the current run. The Java 21 `setsid` edge case — the spawned child already being a process-group leader, causing setsid to fork and pid ≠ group id — does not occur under the JVM and is not engineered around.

## Consequences
- New explicit dependencies: `org.jetbrains.kotlinx:kotlinx-coroutines-core` (1.11.0) and `net.java.dev.jna:jna` (5.14.0, already transitive via Ktor's tree). `backend/deps.json` is regenerated by the user and `nix build .` re-verified.
- The dev environment and the packaged app need `setsid` (util-linux) on PATH; item 16 extends the wrapper environment. Added to `devenv.nix` in this item (ADR 0010).
- One tiny extra exec per run (setsid); signals cost no processes.
- Test determinism requires no fixed sleeps for synchronization; bounded waits/timeouts everywhere.
- Deterministic tests for races use internal seams: process start (to land a cancel or a pause inside the spawn window), the drain loop (tested with a scripted stream and a fake `Process`), and `kill(2)` (a fake backend for a group that outlives `SIGKILL`). The seams are `internal`; the public API is unchanged.
- Rejected: coreutils `kill` spawn (extra process per signal, PATH dependency), `Process.destroy()` for cancel (direct child only, not the tree), returning `Flow<String>` for stdout (an uncollected flow fills the pipe and stalls the child), draining to EOF on cancel (slower, can hang on lingering pipe holders).
