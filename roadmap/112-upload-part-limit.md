# 112 — Uploads over 50 MiB answer 500: the multipart part limit is not the app's cap

Status: spec-approved
Depends on: —
Blocks: —

## Goal

Every upload the app advertises — any file up to `maxUploadBytes` (1 GiB by default) — is accepted
and stored, from the browser and from the TUI. Today a file between 50 MiB and the cap fails with a
500 "Unexpected server error"; the client's progress stops at about 95%.

## Evidence

- The user's TUI upload of a ~52.4 MB file failed at 95% with `500 Unexpected server error`; the
  backend log:
  `io.ktor.utils.io.ClosedReadChannelException: Limit of 52428800 bytes exceeded while searching for
  "\n--e801…"`, caused by `java.io.IOException: Limit of 52428800 bytes exceeded while searching
  for "\n--e801…"`, thrown inside `stt.db.StagedUploadKt.stage(StagedUpload.kt:138)`.
- `UploadRoutes.kt:76` calls `call.receiveMultipart()` with no argument. Ktor 3.6.1's default
  `formFieldLimit` is 50 MiB (52,428,800 B), and its `ByteChannelScanner` applies that limit to the
  boundary scan of **every** part, file parts included (`ByteChannelScanner.checkBounds`).
- The app's own cap is `DEFAULT_MAX_UPLOAD_BYTES = 1_073_741_824L` (`config/Config.kt:89`),
  enforced by the declared `Content-Length` check (`UploadRoutes.kt:69-72`) and by
  `stageChannel(part.provider(), limit)` (`StagedUpload.kt`, 413 `upload-too-large`). The advertised
  cap and the parser's part limit disagree for 50 MiB–1 GiB.
- The browser sends the same route and the same multipart body, so it fails identically.
- The 95% coincidence: the scanner reached its 50 MiB limit while the client had sent 52.4 MB
  (50/52.4 ≈ 95%).
- Item 41 (upload hardening) and `UploadSizeLimitSpec` test the cap with small data (64-byte cap,
  100-byte file), far below Ktor's default, so the suite never crossed 50 MiB.
- `stageChannel` already discards a failed staging (`StagedUpload.kt`), so the 413 paths leave no
  partial original.

## Decided (2026-11-21, user)

- **Use Ktor's multipart parser, not a hand-written one.** A custom reader would parse untrusted
  bytes (boundary scanning across reads, header quoting, CRLF variants, malformed and truncated
  bodies) and needs a far larger test list; the framework's parser is the proven one. The fix is
  to pass a `formFieldLimit` that covers the app's cap.
- **The form-field memory bound is accepted.** A hostile form field is buffered into a `String` up
  to the parser's limit; reaching that requires being on the user's machine (app mode is loopback
  with a per-install credential; the dev server is the developer's own machine). Recorded, not
  mitigated with a custom parser.
- **`formFieldLimit = maxUploadBytes + 1 MiB`.** The margin lets a part of exactly the cap find its
  closing boundary; a chunked form field stays bounded at about 1 GiB + 1 MiB.
- **A chunked form field over the parser's bound answers 413 `upload-too-large`**, the same size
  answer as an over-cap file.
- **The 51 MiB regression test's fixture is generated, never committed.** The test generates a
  temporary long silent audio file (51 MiB), uses it, and deletes it after the test; a test-only
  seam that lowers the parser limit is rejected because the 51 MiB body is the bug's repro.
- **The route test is the e2e proof.** The existing browser upload e2e covers the client path; a
  51 MiB browser e2e would need a generated long clip and a slow engine pass, so the item records
  that gap. The TUI journey's upload stays green.
- The browser and the TUI share the route; one server-side fix covers both.

## Proposal

- `call.receiveMultipart(formFieldLimit = limit + PART_SCAN_MARGIN)` with `limit =
  config.maxUploadBytes` and `PART_SCAN_MARGIN = 1 MiB`. The app's `stageChannel` still enforces the
  cap (413), and the declared `Content-Length` check stays as the cheap pre-check.
- Map the parser's own limit exception (a part over `limit + margin`, e.g. a chunked form field) to
  `413 upload-too-large` instead of the last-resort 500. A client disconnect is not a 413: the loop
  is cancelled and the answer is unobservable.
- A chunked body over the cap is refused by `stageChannel` (413) as today.
- Item 102 (the Rust backend's uploads) must keep the same contract: every file up to the cap
  uploads, a larger one answers 413 `upload-too-large`.

## Test list

- [ ] (basic) An upload of 51 MiB under a 64 MiB cap is accepted, stored whole (the stored size is
      51 MiB), and answered 201 — today the parser's 50 MiB default answers 500. The 51 MiB body is
      generated by the test (a temporary long silent audio file), used, and deleted after the test;
      nothing is committed.
- [ ] (edge) A chunked upload of a part exactly at a small cap (e.g. 64 bytes) is accepted and
      stored: the closing boundary after the last byte parses (the margin's edge).
- [ ] (failure) A declared body over the cap is refused with 413 `upload-too-large` and nothing is
      stored (existing behavior; must stay).
- [ ] (failure) A chunked body over the cap is refused with 413 `upload-too-large`, and nothing is
      stored.
- [ ] (failure) A chunked form field larger than the parser's bound is refused with 413
      `upload-too-large`, not a 500 and not buffered without bound.
- [ ] (must not break) The existing upload specs stay green: duplicate file part, missing file,
      wrong file field name, the size-limit spec, the streaming window behavior.
- [ ] (must not break) The TUI journey's upload and the existing browser upload e2e pass; the item
      records that the e2e fixture stays small (the 51 MiB size proof is the route test).

## Acceptance criteria

- Any file ≤ `maxUploadBytes` (1 GiB default) uploads and stores, from every client.
- A file > `maxUploadBytes` answers 413 `upload-too-large`, with or without a declared length.
- No 500 from the parser's default limit.
- `gradle check`, the integration tests and the e2e gates green; the formatting gate green.
