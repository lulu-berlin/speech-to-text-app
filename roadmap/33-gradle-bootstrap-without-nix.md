# 33 — Gradle bootstrap for developers without Nix

Status: draft
Depends on: [16](16-nix-flake-package.md) (the flake is the version source), [34](34-dev-mode.md) (`./gradlew dev` reuses its dev setup)

## Goal

A human developer without Nix, devenv or Docker clones the repository and builds and runs the whole app with one command, `./gradlew run`, and has a dev mode with `./gradlew dev`. Every tool and asset that path downloads has the same version as the Nix flake (and therefore the Docker image, which is built from the flake, item 19), and a check fails when they drift.

## Already decided

- User requests (2026-10-11):
  - a Gradle wrapper and a top-level Gradle setup: one central entry point for onboarding new users;
  - it downloads Node and pnpm in the right versions, builds the frontend and the backend, and runs everything with one invocation;
  - it is meant for users who have neither Nix nor Docker;
  - its versions match the Nix flake and Docker exactly, and something keeps them synchronized.
- **Scope of the agent rules (user, 2026-10-11):** AGENTS.md's rules — dependencies only from `devenv.nix`/`flake.nix` (ADR 0010), and ADR 0014's "no Gradle wrapper" — govern agents, which always work in devenv. The wrapper and the downloads that bypass Nix exist for human developers who use neither Nix nor an agent; they are not a second toolchain for agents. Recorded as an ADR (scoping ADR 0014's wrapper decision) and a one-line note in AGENTS.md when this item is approved, so no agent removes `gradlew` as a violation.
- **Prebuilt binaries are fine** (user, 2026-10-11): whisper-cli and ffmpeg are downloaded, not built from source.
- **Platforms (user, 2026-10-11):** Linux x64 supported; **macOS best-effort**: no macOS testing, no large restructuring for it.
- **Java prerequisite (user, 2026-10-11):** any recent Java runs the wrapper; Gradle's toolchain resolver (foojay) provisions JDK 21.
- [ADR 0046](../docs/decisions/0046-every-feature-has-an-e2e-test.md): this is a build item, exempt from its own Playwright test; its acceptance runs item 21's e2e suite against the app started by `./gradlew run`.

## Proposal

To be settled in the consultation. Starting points:

- **Root Gradle build**: `gradlew` + `gradle/wrapper/` at the repository root (Gradle version = the flake's); a root `settings.gradle.kts` that includes `backend` and a `frontend` project; the existing `backend` build stays usable from devenv (`gradle check` in `backend/`).
- **Frontend through Gradle**: a Gradle Node plugin (e.g. `com.github.node-gradle.node`) downloads Node and pnpm at the pinned versions and runs `pnpm install --frozen-lockfile` and `pnpm build`; the backend's run task serves `frontend/dist`.
- **Runtime downloads**: whisper-cli (Linux: Vulkan build where one exists; macOS: Metal), ffmpeg (static builds), the whisper and CAM++ models; each with a pinned URL and sha256, cached under the Gradle user home so a second clone reuses them.
- **`./gradlew run`**: builds both halves, fetches the runtime, sets the `STT_*` variables (models, static dir, data dir defaulting to the same place as item 16's wrapper) and starts the server on `http://localhost:8080`.
- **`./gradlew dev`**: item 34's dev mode for users without Nix.
- **Version sync**: the flake exports the versions it uses (Node, pnpm, Gradle, JDK, whisper-cpp, ffmpeg, model URLs and hashes) as a committed `versions.json`, regenerated by a user-run `nix run .#update-versions`; a flake check fails when the committed file, the wrapper's Gradle version or the download table disagree with the flake. Gradle reads `versions.json`. Docker needs no extra sync (its image is the flake closure).

## Open questions

- Where do Linux/macOS whisper-cli binaries come from? ggml-org's releases may not include Linux binaries `[INFERENCE, to check]`; a third-party build raises a trust question. Options: official artifacts only, a named third-party build with pinned hashes, or our own release built by the user from the flake.
- "Exactly" for prebuilt binaries: Node, pnpm, Gradle, JDK can match to the patch; whisper-cli matches the release tag (a different build of the same version); ffmpeg static builds may match only to the release branch. Accept matching at the precision each source offers (the check compares at that precision)?
- macOS and `setsid` (ADR 0020's process groups): document `util-linux` from Homebrew as a macOS prerequisite, or ship a small shim?
- `STT_WHISPER_CLI` / `STT_FFMPEG`: the backend finds the tools on `PATH` today; does `./gradlew run` prepend its download dir to `PATH`, or do the variables become real config?
- Update flow: who runs `nix run .#update-versions` after a nixpkgs bump (the user, ADR 0010) and what fails until then?

## Acceptance criteria

- User-run on a Linux machine without Nix (Java installed): from a fresh clone, `./gradlew run` serves the UI on `http://localhost:8080` and a short clip completes with a transcript; item 21's e2e suite passes against it.

- Changing a version in the flake without regenerating `versions.json` makes the flake check fail; regenerating it makes the check pass.
- The README's "Run without Nix" section documents the path (item 35).
